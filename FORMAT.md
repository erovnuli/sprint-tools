# Sprint-Layout 6 (.lay6 / .LMK) file format

An independent, unofficial description of the binary files written by Sprint-Layout 6.0
(ABACOM). It was worked out by comparing files saved by the program that differ in exactly one
thing. Everything marked **verified** was generated by `lay6.py` and opened correctly in the program.
All values are little-endian. Corrections and additions are welcome.

Reading tip: `walk()` in [lay6.py](lay6.py) is a short, complete reader for all object types.

## Units and coordinates
- Geometry is IEEE **float32**, unit **0.1 µm** (1 mm = 10000.0).
- X is measured from the left edge as the UI shows it.
- **Stored Y = Y_ui − canvas_height** (so on a 100 mm canvas, UI y 66.04 → −339600.0).
- (An earlier analysis described a "custom 24-bit float with the mantissa top bit reused
  as exponent low bit". That was a misreading: it is a plain float32 whose low byte is
  often zero.)

## File layout
A file holds **one or more boards** (Sprint's tabs at the bottom of the window). **verified** with one- and
two-board files saved by the program.

| Offset | Content |
|---|---|
| 0x000 | magic `06 33 AA FF` |
| 0x004 | **u32 number of boards** (1 in a one-board file; an earlier version of these notes called it "version = 1") |
| 0x008 | board 1 header, **0x212 bytes**: u8 name length + name ("Board 1", "New board", "Плата 1" in CP1251), canvas width / height u32 at **header +0x23 / +0x27** (0.1 µm units; 1000000 = 100 mm), f64 at header +0x3A that changes on every save, rest copied verbatim from a donor |
| header + 0x212 | **u32 object count n** of this board (file offset **0x21A** for board 1) |
| header + 0x216 | n object records, variable length, walked sequentially (never strided) |
| after the objects | **this board's pad list: one u32 (zero) per pad object of the board** (SMD type 8 and through-hole type 2). Lines, circles, zones and text add nothing here. **verified** with a 14-board file |
| … | the next board's header follows directly after the previous board's pad list |
| after the last board | one u32, then the trailer: 307 bytes (heap pointers, uninitialised memory) in most files, longer in some (seen: 427). Copied from a donor when generating. Getting the pad lists wrong gives "stream reading error". |

Board 1 can be empty (count 0) with the real board in board 2: seen in two user files (a board created in a new
tab; a Gerber import "XGerber"). A 14-board user file (boards from 16 × 16 to 500 × 120 mm, 17226 objects) confirmed
that the pad list belongs to each board: with an empty first board it has length 0, which is why two-board files
first looked as if a single pad list for all boards came at the end. Readers must walk all boards.
Board names are Pascal strings in a fixed buffer: bytes after the stored length are leftovers ("el" followed by
"102.188-2" from an earlier name) and must be ignored. The tools work on the first board with objects
unless `--board N` is given. Writers insert new objects at the end of the selected board and raise its count.
A marked copy of a two-board file written this way opens normally in Sprint (tested).

## Common object header (types 2, 4, 5, 6, 8)
| Offset | Type | Meaning |
|---|---|---|
| +0x00 | u8 | object type: 2 through-hole pad, 4 zone, 5 arc/circle, 6 line/polyline, 7 text, 8 SMD pad |
| +0x01 | f32 | X (pad centre / circle centre) |
| +0x05 | f32 | Y (stored form) |
| +0x09 | f32 | SMD pad width / arc OUTER radius / through-hole OUTER radius |
| +0x0D | f32 | SMD pad height / line width / arc INNER radius / through-hole DRILL radius |
| +0x15 | u8 | selected-in-editor flag (1 when saved while selected); write 0 |
| +0x16 | u8 | **layer: 1 = C1 top copper, 2 = S1 top silk, 3 = C2 bottom copper, 4 = S2 bottom silk, 7 = O outline** (verified); 5 I1, 6 I2 expected by Sprint-Layout order |
| +0x17 | u8 | through-hole pad shape (see below); 0 for SMD pads |
| +0x18, +0x23, +0x2D | u32 | heap pointers — churn every save, safe to copy |
| +0x28 | u16 | constant 4000 |
| +0x3A | u8 | **solder mask: 1 = exposed (no mask over it), 0 = covered by mask** — verified for SMD pads, through-hole pads, tracks and zones, read and generated (`set_mask()` in lay6.py). Sprint's defaults: pads 1, tracks/zones 0 |
| +0x3E | u32 | constant `15 CD 5B 07` in every pad (not an ID — altering it breaks loading) |
| +0x51 | u32 + bytes | **element name string**: u32 length n, then n bytes in the Windows ANSI code page. Empty (n = 0) in files saved by Sprint-Layout 6.0; boards from some other Sprint versions store the part's value or name here on every element of a placed part (e.g. "100nF", "10k"). **All offsets below shift by n.** **Sprint-Layout 6.0 keeps this string unchanged** (tested with UTF-8 Georgian on a text and a track): through load and save, moving, copy and paste (copies get it too), and editing a text in its dialog (the strokes are redrawn, the string stays). It is shown nowhere in the program, so it can carry extra data. **Limit: at most 255 bytes** (a Delphi short string; tested Oct 2026): 256 bytes still load but Sprint saves only 255, and **257 bytes or more make Sprint-Layout quit while opening the file**, without a message. Writers must never exceed 255 bytes per object. |
| +0x55+n | u32 | **k = number of groups the object belongs to** (0 = ungrouped) |
| +0x59+n | k × u32 | group ids, innermost first (see Grouping) |
| then | u32 + points | point count m, then m × (f32 X, f32 Y) — absent for circles |

Many other header bytes hold uninitialised memory; copy them from a template.

### Pad (type 8) — 125 bytes with k = 0. **verified**
- +0x01..+0x10: centre X, Y, width, height.
- Point list: 4 corners `(−w,+h) (+w,+h) (+w,−h) (−w,−h)` (halves) — these are what the app
  draws. A pad copied and moved in the app keeps its *old* centre fields but new corners.
- Pads inside a group can have centre fields 0,0 in some app-saved files; corners are absolute.
- A "pad" on the silkscreen layer (+0x16 = 2) is how NC pins are marked so tracks may
  route under them.

### Line / polyline (type 6) — 0x59 + 4 + 8m bytes with k = 0 (2 points → 109). **verified**
- **Width = u32 at +0x11** (0.1 µm units) for silkscreen lines and copper tracks alike
  (verified: a line with 0.2 in the f32 at +0x0D and 0.6 at +0x11 shows as 0.6 mm). The f32
  at +0x0D is ignored (app writes 0 there for tracks; older notes wrongly called it the width).
- **A track is a line on a copper layer.** With the app's "rubber band" button on (a global
  setting, not stored in the file), tracks follow the pads they end on - there is no stored
  pad link, only matching end points. Verified with straight and bent generated tracks.
- The app writes polylines of 3 and 5 points; 2-point lines verified from generator.

### Arc / circle (type 5) — 89 bytes with k = 0, no point list. **verified**
- +0x01/+0x05 centre; +0x09 **outer radius** = r + w/2; +0x0D **inner radius** = r − w/2.
- +0x11 **end** angle, +0x1F **start** angle, u32 millidegrees. 0° = +X (right), drawn
  **counter-clockwise** from start to end; start == end → full circle (0/0 or 180/180).
- Example: a pin-1 dot of r 0.635, w 0.5 has the fields 0.885 / 0.385.

### Through-hole pad (type 2). **verified**
- +0x01/+0x05 centre, +0x09 **outer radius**, +0x0D **drill radius** (f32). Dialog values are diameters.
- +0x17 shape: 1 round, 2 octagon, 3 square, 4 "rounded" = **oblong**.
- Point list = outline: round 2 points (x±r, y) — ignored for drawing; square 4 corners
  (same order as SMD); octagon 8 corners at ±r and **±round_half_up(0.415·r)** (the app's
  factor, not tan 22.5°); oblong = the segment between its 2 points swept by the pad radius —
  app default points (x±r, y) → 2·D long, D wide. **Always 2:1**: other point spacings display
  on load, but the app rebuilds them to ±r as soon as the pad is edited (seen on a TO-220 file).
  The direction of the two points is kept (verified vertical and 45°). Record = 0x59 + 4 + 8·m → 109 / 125 / 157 bytes.
- +0x39 plated ("through pad", hole metallisation); +0x32 thermal pad (app also sets +0x39).
  An unplated pad does NOT connect top and bottom copper.
- Counts as a pad in the per-pad tail list. In macros the app shifts its **centre** too
  (unlike SMD pads) — verified with a DIP-8 macro.

### Zone (type 4) — copper fill of any shape. **verified**
- Centre/size fields 0; the point list is the outline polygon (any number of corners).
- +0x11 u32 outline thickness (0.1 µm); +0x32 hatch on; +0x33 hatch-thickness mode
  (1 = same as outline, 0 = self-defined); +0x34 "cutout area"; +0x35 u32 self-defined hatch
  thickness (app keeps a stale value there in outline mode; its dialog won't accept new values,
  but the app reads any value from a file).
- +0x4A "cutout soldermask": set by that zone option. An earlier sample seemed to store 5 in the
  point count with only 4 points; later 5-corner zones read correctly, so this needs a re-check
  before the generator offers the option. The ordinary solder mask on/off for zones is +0x3A.
- Zones add nothing to the per-pad tail list.

### Text (type 7). **verified**
| Offset | Content |
|---|---|
| +0x00 | type 7 |
| +0x01, +0x05 | anchor X, Y (bottom-left of first glyph) |
| +0x09 | f32 text height (2 mm sample) |
| +0x0D | f32 **thickness**: 0.0 = thin, 1.0 = normal, 2.0 = bold (verified) |
| +0x11 | u8 **character width**: 0 = narrow, 1 = normal, 2 = wide (verified) |
| +0x16 | layer |
| +0x4D | u32 string length L, then L ASCII bytes (no terminator) |
| then | u32 n + n bytes element name string (normally n = 0, see the common header), u32 k, k × u32 group refs |
| then | u32 stroke count S, then S stroke sub-records |

Stroke sub-record: 0x4D-byte header (type 6, no group list) + u32 m + m points.

**Mirroring (verified Oct 2026, mirrortest.lay6):** two flags in the text header, **u8 +0x32 = horizontal
mirror, u8 +0x33 = vertical mirror** (1 = on); nothing else changes, and there is no rotation field involved.
The stored strokes are already mirrored **about the anchor** (+0x01/+0x05): a horizontally mirrored text runs
leftwards from the anchor, a vertically mirrored one hangs down from it. `latin_text(..., mirror_h=, mirror_v=)`
reproduces the app's records (identical apart from heap pointers and float rounding).

**Rotation (verified Oct 2026, rotatest.lay6):** **u32 +0x35 = text angle in whole degrees, clockwise**
(0, 45, 90 and 279 verified; 279 is stored `17 01 00 00`, so the field is wider than one byte - read and
write it as u32, the upper bytes are 0). It is a text-specific field,
not a general object rotation. Like the mirror flags it only records the setting: the strokes are stored
already rotated clockwise about the anchor (+0x01/+0x05), which stays where it was.
`latin_text(..., rotation=)` reproduces the app's records. Mirror and rotation together: order not yet tested.

**Thickness and character width (verified Oct 2026, moretext.lay6)** are record-only settings like
mirror and rotation (header +0x0D and +0x11, see the table); the strokes are stored already laid out:
- stroke width (stroke sub-record +0x11, u32 0.1 µm, rounded): thin 5/81 × height, normal 1/9 × height,
  bold 10/63 × height (1 mm text: 617 / 1111 / 1587 units; 2 mm text: 1235 / 2222 / 3175 - verified);
- character width scales every glyph horizontally: narrow × 2/3, wide × 4/3 (heights unchanged);
- the gap after each glyph depends on the thickness, not on the width: 8/3 (thin), 11/3 (normal),
  14/3 (bold) x-steps of height/15;
- a space is a blank glyph 0.2 x-steps wide (scaled by the width) plus its gap.
`latin_text(..., weight=, width=)` reproduces all five samples (headers identical, points within 0.001 mm).

**The app draws the stored strokes and never re-renders on load.** The string is only
what the edit box shows; pressing OK in the edit box re-renders strokes from the string
with the app's font. So arbitrary scripts (e.g. Georgian) can be placed as strokes with
an ASCII placeholder string — but editing the label in the app replaces them.

## The program's label font
Labels are drawn with a **built-in single-stroke font** inside the program (not a Windows
font). Glyphs sit on a grid: X step = height/15, Y step = height/18, cap height 16 steps,
baseline 0; the gap between letters is 2.2/9 of the height.
- **Has glyphs:** `! " # $ % & ( ) * + , - . / 0-9 : < = > ? @ A-Z \ _ a-z ~ ° µ Ä Ö Ü ß ä ö ü €`
  ('.' is a single point, ':' two points; a space is a 0.2-step blank glyph plus the gap).
- **No glyph (drawn as one zero-length stroke = a dot, zero width + normal gap):**
  `' ; [ ] ^ ` { | }`, all other Latin-1 (± § © ® ² ³ × ÷ é Ø ø …), Greek, **all Cyrillic, Georgian**.
- The dialog renders from the Unicode text, but the **label string is stored in the ANSI code
  page**, so non-ANSI characters are saved as '?' (Georgian test label: `??????? ??????`, 13 dots).
  Characters missing from the ANSI page are best-fitted (Ω → O, β → ß, π → p).
- Workaround for other scripts: write the strokes directly into the file (generator) with an
  ASCII placeholder string; they display and plot correctly until the label is edited in the app.

## Grouping. **verified** (one level and two-level nesting reproduced byte for byte)
A group is **only a tag list on each member object** — there is no group record and nothing
else in the file changes (tail and trailer identical). Each member stores k and k group ids
(at +0x55 for pads/lines/circles; after the text string and the element name string for text), **innermost group first**.
Ids are small integers the app hands out (1, 2, 3 …). Example saved by the app: left pads
in group 1, right pads in group 2, both plus silkscreen in group 3 → left pads `[1, 3]`,
right pads `[2, 3]`, silkscreen `[3]`. Each tag adds 4 bytes to the record (pad 125 → 129
→ 133). Use `group()` in lay6.py; apply it again to nest.

## Macro / library component files (.LMK). **verified** (generated TQFP-44.LMK loads, previews and places in the app; 2 app-saved macros reproduced byte for byte except pointers)
| Offset | Content |
|---|---|
| 0x00 | magic `06 33 AA FF` |
| 0x04 | u32 object count |
| 0x08 | object records, same layout as on a board |
| then | 4 + 4 × n_pads zero bytes |
| end | 98-byte block (pointers; copy it) |

No board header (no name, canvas or grid). **All geometry is relative to an origin the app
chooses itself: the centre of the leftmost pad, topmost on ties** (the user has no option
for it; it is not the first object or first pad). Point lists (pad corners, line points) and
circle centres are shifted; pad centre fields keep absolute board values, which the app
ignores. Relative Y is still "up is positive". Units identical to boards.
The direction or order of the user's selection when saving has no influence (tested).
Group tags (including nested groups) are kept unchanged in macros; `build_macro()` on
grouped records reproduces an app-saved grouped macro byte for byte (except pointers).

## Components (Sprint 6 "Bauteil"). **verified** (capacitor, 2 copies, SOT-23 transistor)
A component is not a separate record: its objects (silkscreen, pads, texts) are stored one
after another, each marked with the **component number at +0x1C** (u8; 1, 2, ... in order;
0 = not part of a component). Text type byte **+0x17**: 0 = ordinary text, 1 = component
**ID text**, 2 = component **value text** (an empty value is stored as one 0-length stroke).

The **ID text is followed by the component properties** (right after its last stroke):
| Type | Meaning (component dialog) |
|---|---|
| f32 | Pick+Place X-offset (0.1 µm) |
| f32 | Pick+Place Y-offset (0.1 µm) |
| u8 | centre mode: 0 = centre copper (1/2 = silkscreen / copper+silk, assumed) |
| f64 | rotation in degrees (e.g. 22.0) |
| u32 + chars | Package (e.g. "SOT-23") |
| u32 + chars | Comment (e.g. "Test transistor") |
| u8 | "Use Pick+Place data" (1 = on) |
Empty fields give the 26-byte minimum. Readers must skip this block or lose step (`walk()` does).

**Pins:** pads keep footprint-local coordinates in their centre fields (pad 1 at 0,0) while the
corners hold board positions, so the footprint rotation can be recovered. **Storage order is the
pin order** (SOT-23 MMBTA42: 1st pad = B, 2nd = E, 3rd = C, matching pins 1/2/3). SMD pads inside
the SOT-23 had +0x17 = 2, 2, 0 (meaning unknown). Copying a component gives the copy the next
number; the ID text is copied unchanged; ID, value and ordinary texts are stored as strokes.

## Extra data in a file (tested Oct 2026)
- **Appended after the trailer:** Sprint-Layout opens the file normally (it reads only what the counts say), but
  **drops the appended bytes when it saves**. Only for data that can be lost or rebuilt.
- **Element name string of an object:** kept through opening, moving, copying, editing and saving, **up to 255
  bytes per object** (see the common header). Larger data has to be split over several objects.

## Unknowns / next steps
- Component centre modes 1/2 and the SMD pad +0x17 values inside components.
- Zone "cutout soldermask" point-count anomaly (see Zone).
- SMD pad paste fields; vias as a separate object (if any). (Solder mask on/off = +0x3A, decoded.)
- Layers 5–6 (inner copper) inferred from Sprint-Layout's order, not yet seen in a file (4 = bottom silk and 7 = outline verified).
- Mounting holes: a common practice is a circle on the outline layer. A through-hole pad with outer = drill shows a big X in the program.

## Method
1. Save a baseline file in the program, then files that each change exactly one thing.
2. Diff; ignore the trailer, pointers and the per-board f64 (file 0x42 for board 1).
3. Record lengths: from file growth; confirm by saving **two** objects of the type —
   one object alone cannot separate a record from padding that follows it
   (this caught the 129-vs-125 pad error and the per-pad tail list).
4. Generate test files that each isolate one hypothesis when a file fails to open.
